# ADR 0007: Tailwind and shadcn-vue as the component layer

Accepted 2026-09-21 by explicit user request. Amends the "original CSS, no component framework" position in ADR-0006; it does not change the editor engine, the window model or the desktop-writing-tool direction those ADRs set.

Use shadcn-vue for interactive controls (select, dropdown, menu, tooltip, dialog, checkbox, switch, input) and Tailwind 4 as its styling engine. shadcn-vue is not a dependency that is imported as a library: the CLI copies component source into `src/components/ui/`, so those files are ours — they may be edited, and every edit is logged in `PATCHES.md` the way editor-engine integrations are.

Tailwind is imported in layers rather than as one bundle (`src/app/tailwind.css`): `theme` and `utilities` only, **never preflight**. Preflight resets list markers, blockifies inline images and rewrites borders — all of which the Markdown document and the toolbar rely on as user-agent defaults that this project never declared, and author-layer CSS beats UA styles outright. The one preflight rule shadcn controls need (`border: 0 solid` on every element, so a utility can add one border edge) is restated in a compensating `@layer base` block.

The existing `--y-*` design-token system stays the single source of truth. It is written at runtime on `.app-shell` by the theme presets, so the bridge runs the other way: Tailwind's theme is declared with `@theme inline` over the `--y-*` names, and the shadcn aliases (`--background`, `--foreground`, `--primary`, `--border`, `--radius-*`, …) are declared on the same element that owns `--y-*`. `@theme inline` is required, not stylistic: a non-inline theme resolves once at `:root`, so a preset switch would never recolour a component. `--y-accent` maps to `--primary`; shadcn's own `--accent` is the hover surface and maps to `--y-hover`. No HSL conversion: Tailwind 4 accepts the plain colour values this project already emits.

Two consequences of the portal model are settled here, before any component lands. Reka UI teleports overlay content to `document.body` by default, outside the token scope, so the design tokens were moved from `.app-shell` to `:root` and the theme colours are additionally mirrored onto `document.documentElement` by the shell — that, not a `ConfigProvider` pin, is what makes a portalled popup resolve them; the dark variant keys off `documentElement`'s `data-theme` for the same reason. And because shadcn's stock `z-50` sits below this project's `--y-z-modal: 200`, copied overlay components use the `--y-z-*` tokens; Tailwind's `z-N` utilities are not used for overlays.

Element resets this project already owned (`button`, `input`, `select`, `textarea`) moved into Tailwind's `base` layer, because unlayered CSS outranks every layer regardless of specificity and would have beaten every copied component's utilities. That is also why preflight's absence is safe: the app never depended on the reset it omits.

Deliberately outside the migration: the ProseMirror/Milkdown document DOM; CodeMirror surfaces; anything the editor adapter builds with `createElement`; the virtualised file-tree rows, whose fixed-height scroll maths would have to be rewritten; the Tauri titlebar drag region; and `AppDialog.vue`, whose programmatic promise API does not fit a declarative dialog. Marketing-page patterns remain inapplicable per ADR-0006 — this is a dense desktop tool, variance 3, motion 2, density 6.

Verification so far: the first migrated controls are the preset and appearance selects in the settings panel, covered by `tests/settings-select.test.ts` (real render, label resolution from the stored id) plus lint, typecheck, the suite and the production build. Still to be confirmed by eye on an unlocked host, because no automated driver exists for this platform: a preset switch and a light/dark switch recolouring the open picker with no reload, the picker painting above the modal shade, the custom-CSS editor still restyling the document, and no list marker or inline image in the document changing.
